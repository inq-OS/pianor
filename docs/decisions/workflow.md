# Decisions: Workflow

Docs, tests, CI, issues, projects and process. One entry per decision, oldest first. Index: [DECISIONS.md](DECISIONS.md).

## d000

**Four axioms (AX-0 to AX-3) rank above every decision, and AX-0 (learning music) decides every conflict.** Features: none.

`docs/axioms.md` holds AX-0 The Core, AX-1 The Grind (prefer the harder option), AX-2 The Attraction (just enough game, objective feedback) and AX-3 The Scaffold (build the simplest modular thing, mark it, tell the architect); `CLAUDE.md` repeats them. The player is called the student; feedback is objective (what happened, no unearned praise, no shaming). Every answer the maintainer gives to a product question is logged with an axiom gap (`missed`, `new rule`, `taste`) so the architect can grow the axioms. AX-4 The Master was added by d161.

Check: untestable: the axioms are a ranking the maintainer and reviewers apply, no code decides it

## d003

**Build a thin practice slice first and playtest it before the ABC compiler and linter.** Features: ft_0_09.

The slice is a hand-written chart, staff, judge and mock keyboard; the first playable build must not wait for eight tooling packages.

Check: untestable: build-order choice for agents, judged by the maintainer

## d005

**Everything must be testable without the EZ-220.** Features: ft_0_06.

A virtual EZ-220 (fake `MIDIAccess`), virtual player and replay player exist (`docs/testing.md` section 7); synthetic fixtures are labelled `synthetic` and real-hardware facts stay "needs human".

Check: `src/io/mock/VirtualEz220.test.ts` "exposes a connected input and output through a MIDIAccess-shaped object"

## d006

**Code is MIT, original pieces are CC0 or CC-BY, dependencies must be permissive.** Features: ft_0_00.

GPL projects (Neothesia, PianoBooster) are reference only, with local private use allowed under d026. Each piece records its own licence.

Check: untestable: licence choice, reviewed with docs/dependencies.md by the maintainer and reviewers

## d017

**End-to-end tests use Playwright on port 5180, driving the game like a student would.** Features: ft_0_09.

Config in `playwright.config.ts`: own dev server, viewport 1366x768, 2 workers, traces on failure. Tests use computer keys, the virtual EZ-220 bytes, real clicks on Phaser buttons and on-screen keys via `window.__game` and `window.__virtualDevice`, read canvas text from scene text objects, and assert no page or console errors. Screenshot baselines are per OS (`*-chromium-win32.png`); a platform without a baseline skips. The staff rooms are computed from the notes in the piece so switching hints never moves the staff.

Check: `playwright.config.ts` "Number(process.env.PW_PORT) || 5180"

## d024

**Check prior art per work package; keep our own sampler and staff renderer for now.** Features: ft_0_11, core_09, ft_Y_04.

Sightread is GPL-3.0 (reference only); VexFlow 5 (MIT) is to be re-evaluated when accidentals, key signatures, ties or beams are scheduled (done for beams: kept as a reference only, changed by [d155](notation.md#d155)). Before a package that builds a new subsystem, spend a short bounded search for permissively licensed prior art and record the verdict (`docs/dependencies.md`).

Check: untestable: process rule for agents (a bounded prior-art search before a new subsystem)

## d026

**The gitignored `private/` folder may hold code and output under any licence, and nothing committed may import it.** Features: all.

A lint rule makes any import of `private/` an error everywhere else, so the repository and bundle stay MIT; private code may call into the project, and third-party output stays inside `private/`. Licences such as the GPL bind when copies are shared or the game is hosted for others.

Check: `eslint.config.js` "Nothing outside private/ may import private/"

## d037

**Feature ids are `core_XX` for core behaviour and `ft_Y_XX` for features, Y being the iteration.** Features: all.

Iteration 0 is the MVP; an undecided iteration keeps the letter Y (`ft_Y_03`); parts keep a letter (`ft_1_02a`); files are `<id>-name.md`. Effort ratings (trivial, simple, medium, large, high friction) are a column in `FEATURES.md` for unbuilt features. Playing with key lighting disabled is a 1.10x XP modifier (core_07) and the confuser (ft_Y_08) lights random keys, both resting on key lighting verified in ft_0_01.

Check: `tools/docs/lint.test.ts` "flags ids with no file in docs and in code"

## d041

**Docs are checked and generated from front matter: one source per fact, `docs:check` in CI.** Features: none.

Every feature, decision, authoring and playtest file has front matter (`key: <JSON value>`, zod schemas in `tools/docs/schemas.ts`); index tables and `docs:levels`, `docs:schema`, `docs:usage`, `docs:include` blocks are generated by `npm run docs:index` and never edited by hand. `docs:check` (CI) validates front matter, ids (`ft_`, `core_`, `dNNN`, `auNN`), links, anchors, inline-code paths, `npm run` commands and generated blocks; a done feature lists `ft_X_YY.ACn` criteria, each named by a test or marked `[human]` (`docs:criteria`). Staleness is a warning (`covers`, `verified_against`, `docs:stale`, `docs:verify`); `docs:touched` fails a PR changing `src/core`, `tools` or `content/curriculum` without a doc unless it says `docs: n/a`; the Stop hook `.claude/hooks/stop-check.mjs` runs typecheck, lint and docs check.

Check: `tools/docs/lint.test.ts` "passes its own docs check"; `tools/docs/frontmatter.test.ts` "reads JSON values and returns the body"; `tools/docs/criteria.test.ts` "fails a done feature with a criterion that has neither a test nor [human]"

## d042

**Trunk-based git on short branches with a fast `check` gate and a browser `e2e` job in CI.** Features: none.

`main` is always releasable; short branches (`feature/<id>-name`, `fix/`, `docs/`, `claude/`) return by squash-merged pull request after `npm run check`; agents work in their own worktree. CI (GitHub Actions, Ubuntu, Node 22): `check` (typecheck, lint, tests with 90% coverage on `src/core` and `tools`, `docs:check`, `piece:build`, `piece:lint`, build) and `e2e` (Playwright Chromium) in parallel; a new push cancels the run; Dependabot weekly npm (two groups), monthly Actions. Changed by d062 (screenshot baselines are Windows only, no Linux baselines).

Check: `tools/ci/workflows.test.ts` "runs check and art rules on Ubuntu with Node 22 on every pull request push, never on a push to main"

## d048

**Every feature file carries a `completeness` percentage rated by a rule and rolled up by the generator.** Features: none.

`completeness: N` (0 to 100) is the share of the feature's own scope built and verified by agent-checkable means (`[human]` criteria do not lower it); with slices it is built slices weighted by effort (trivial 1, simple 2, medium 4, large 8), else the share of built scope items. `docs:check` requires the field, `effort: done` means 100, and 100 needs a test per non-`[human]` criterion; a split parent (`effort: split`) has no field and gets the effort-weighted mean of its parts; the summary block in `FEATURES.md` is written by `docs:index` (a done feature weighs 2).

Check: `tools/docs/completeness.test.ts` "makes a done feature 100, and 100 only for a done one"; `tools/docs/completeness.test.ts` "weighs trivial 1, simple 2, medium 4, large 8, and a done feature like a simple one"

## d056

**End-to-end tests are split into areas; pull requests run the areas they touch and every run writes a log.** Features: none.

`tools/e2e/areas.ts` puts every spec in one area (practice, staff, menu, battle, editor, preview, dev, visual), each a Playwright project with the source paths it guards; shared paths and unnamed paths run every area, docs and unit tests none. `npm run test:e2e:affected` runs the touched areas plus smoke; `main` runs every area. A reporter writes `test-logs/runs/<start>_<areas>/` and `test-logs/history.jsonl`; baselines keep `-chromium` names via `snapshotPathTemplate`.

Check: `tools/e2e/areas.test.ts` "puts every spec file in exactly one area"; `tools/e2e/affected.test.ts` "runs the area whose source changed"; `tools/e2e/runLog.test.ts` "writes a summary with a table per area"

## d062

**Screenshot baselines are Windows only, checked by a Windows CI job and made by a Windows workflow.** Features: none.

Only `-win32.png` baselines exist (hint letters use a `monospace` font that differs per OS); Linux CI and cloud sessions skip screenshot tests. The `visual (Windows)` job runs the visual area on `windows-latest` (software WebGL, one test at a time, 4-minute limit) on pull requests touching the visual area, on `main` pushes and weekly; the workflow "Update screenshot baselines (Windows)" (`update-snapshots.yml`) makes new ones, which the maintainer looks at before merge. Changes d042.

Check: `tools/ci/workflows.test.ts` "are checked by a Windows job and made by a Windows workflow run by hand"

## d063

**Static analysis: `npm run analyze` runs type-aware ESLint, knip and jscpd in CI.** Features: none.

`analyze` runs ESLint with type information (`eslint.analyze.config.js`), knip (`knip.json`) and jscpd (`.jscpd.json`, fails above 1%) in the CI `check` job, not the Stop hook; `lint` limits complexity to 30 and nesting depth to 5 in `src/` and `tools/`. Dev dependencies `knip` (ISC) and `jscpd` (MIT); detail in `docs/architecture/static-analysis.md`.

Check: `eslint.config.js` "complexity: ['error', 30], 'max-depth': ['error', 5]"; `.jscpd.json` "threshold"

## d090

**CI runs on GitHub's hosted runners: `check` and `art rules` on every pull request push, the browser jobs on a label or weekly.** Features: none.

A pull request push runs `check` (with the changes and docs-touched steps folded in) and `art rules` on `ubuntu-latest`; Linux e2e runs only with the `ci:e2e` label and the Windows screenshot job (`windows-latest`) only with `ci:visual`. A push to `main` runs only the privacy workflow (d165); `check` runs on `main` daily, everything every week and by hand. Labels and description edits are handled in `.github/workflows/pr-events.yml`; the browser jobs are the reusable `.github/workflows/browser-tests.yml`. Changes the CI part of d062.

Check: `tools/ci/workflows.test.ts` "runs check and art rules on Ubuntu with Node 22 on every pull request push, never on a push to main"; `tools/ci/workflows.test.ts` "runs the browser tests only on a label, by hand or on the schedule"

## d116

**GitHub issues are for people; agents track their own work as tags in the docs.** Features: all.

Issues are the maintainer's (bugs, features, change requests); an agent opens one only when told to or for a non-trivial bug it cannot fix in the work at hand. Everything else is a tag, `ASAP`, `TODO`, `NEEDS-HUMAN` or `IDEA`, written `TAG(<role>[, <release>]): <what>. <why>` in the doc the work belongs to (rules and grep: `docs/automation/todo-tags.md`); the pull request that does the item deletes its tag. Plans live once, in the feature file, and an issue keeps only the request and the closing pull request; a message between threads becomes a tag when taken. Milestones and regression tests stay.

Check: untestable: process rule for agents about issues and tags

## d147

**Unfinished work merges early behind a flag that is off by default instead of waiting on a long branch.** Features: none.

A sound but unfinished pull request merges with the behaviour behind a flag in `AppConfig.flags` (`src/config.ts`), off by default, with its URL switch in `docs/url-switches.md`; a screen or content kind nobody reaches needs none. A pull request should not stay open over three working days; the flag's pull request writes a `TODO(<project>, <release>)` tag to remove it, and the WP is not done while the flag exists. Never behind a flag: a save-format change, or anything the player would meet half-built in `npm run start:local`.

Check: `src/config.test.ts` "is off unless ?autoplay=1, also in a dev build"

## d151

**An idea that is given up is deleted, not kept on hold; a rejected idea stays as one line.** Features: none.

When an idea is given up, its code, content, feature files, design pages and the decisions only about it are deleted in the same round by their owning projects. Frozen migration steps for old save fields stay (d064); a rejected idea (e.g. falling notes, ft_Y_05) stays as one line in `docs/features/FEATURES.md`'s "Rejected" list; decisions about live things are never rewritten. A ledger rule to keep something wins (the band's toolbar code stays behind its flag, d115).

Check: untestable: process rule for agents (delete retired ideas)

## d152

**Decisions are kept as one short entry each in seven ledgers by area, not one file each.** Features: none.

Ledgers give one coherent source of truth with no redundancy. An entry is `## dNNN`, a first line `**Title.** Features: ids.`, and one to four sentences of what holds today; `tools/docs` reads them as decision items (`readLedger`), so ids, the index and links (`ledger.md#dNNN`) are checked as before. Feature files stay one per feature.

Check: `tools/docs/ledger.test.ts` "reads one item per entry with its id, title, features and supersedes"

## d153

**Lean: a builder and a painter, an architect that sets one playable goal a week; no work packages, mailboxes, board, scan or triage.** Features: none. The weekly goal changed by d283.

One builder builds a feature top to bottom, the painter owns how screens look, and the architect keeps one weekly thread ([work-model.md](../automation/work-model.md)). There are no work packages, mailboxes, daily scan, board, triage or dispatch labels, friction or decision logs, or dated reviews; the axioms, CLAUDE.md, feature files, tests and CI, the decision ledgers and flags over long branches (d147) are the process. New process only after the same thing broke twice. Every code pull request gets a fresh `reviewer` agent as a second reader before it merges (d166, [labels.md](../architect/labels.md)).

Check: untestable: work model and process rule for agents and the maintainer

## d161

**AX-4: Kiur is secretly the absolute master of music.** Features: none.

Kiur is secretly the absolute master of music: he never displays it in full, and everything musical is effortless to him. It is written in `docs/axioms.md` as AX-4 with its corollaries: he plays without fault, his play is never a struggle (a tug is still decided by what the student played), he never shows his mastery in full, and what he says about music is always right. AX-0 still decides. It adds a fifth axiom to the four of d000.

Check: untestable: character and tone rule in docs/axioms.md, judged by the maintainer and reviewers

## d165

**Requirements live in the repo: whatever the maintainer decides in any project is written there as a plain rule in the same session, so every project sees it.** Features: none.

Every session loads CLAUDE.md, so the repo is the one place a rule reaches every thread without the maintainer repeating it. The agent turns what the maintainer said into a clear rule of one or two lines (no quotes, no conversation, nothing personal: no people's names, contact details, accounts, machines or private places; Keri and other public places are fine): a decision into its ledger, an idea or work item into a tag in its doc, a testable rule into a check, merged at once. A rule in memory that the repo lacks is written in the same way, not dropped; in a contradiction the newer one wins. `docs:check` fails on a quote of the maintainer, an age, a date or a time of day, a reference to the repository's history (an issue or pull request number, a commit, a branch), a binary file of a kind not allowed or one that carries text, and any entry (a word with its endings, or a `/pattern/`) of the gitignored `private/personal-words.txt` or the CI secret, which CI requires; the same rules read commit messages and the pull request's title and description (`tools/docs/privacy.ts`). CI runs them in `.github/workflows/privacy.yml` on every pull request, its edits and every push to `main`, as `pull_request_target`, so the workflow and the checker come from the base branch and the head's files are only read, and the private list goes only to a branch of this repository, never to a fork's pull request; the agent hooks before and after every write and the git hooks in `.githooks/` (every commit) fail closed, and the hook after a Bash command reports what it finds. Days in tests and fixtures are made up, in 2000 or before (`tools/test/fixtureTime.ts`; a test that needs real weekdays goes back 28 years, where the calendar repeats).

Check: `tools/docs/privacy.test.ts` "reports an entry in any committed file without printing it"; `tools/docs/privacy.test.ts` "is an error in CI when missing, a warning elsewhere, and nothing when given"; `tools/docs/privacy.test.ts` "reads each message whole and names it, not a file"; `tests/content/fixtureDates.test.ts` "keeps every day in tests and fixtures in ${FIXTURE_LAST_YEAR} or before"; `tools/ci/workflows.test.ts` "runs the checker of the base commit on the files of the head, installs nothing and keeps no token in a checkout"; `tools/ci/workflows.test.ts` "check every write before and after it, and every commit or push through Bash, and stop on a finding"; `tools/docs/privacy.test.ts` "finds issue and pull request numbers, commit hashes, branch names and git history in prose, not in code, links or colours"; `tools/docs/privacy.test.ts` "fails text inside an allowed picture or sound, and leaves the tags of the encoder"; `tools/e2e/visualSpec.test.ts` "open every picture through one helper that fixes the clock and checks the test player"; `tools/docs/ledgerChecks.test.ts` "needs one Check line on a live entry, none on a retired or superseded one"; `tools/ci/workflows.test.ts` "gives the private list only to a branch of this repository, never to a pull request from a fork"

## d166

**A thread merges its own pull request once a fresh reviewer approves it and CI is green (a save-format one also after the end-to-end tests); the maintainer tries things only once they are on main.** Features: none.

A pull request merges once a fresh `reviewer` says `VERDICT: APPROVE`, CI is green and no question is open; a save-format change also waits for the end-to-end tests (`ci:e2e`) green ([labels.md](../architect/labels.md)). Never ask the maintainer to check or try something before the merge, nor make that a merge blocker: merge, then say what to try. Pictures stay the maintainer's to merge.

Check: untestable: merge process rule for threads

## d167

**A slow test is made cheaper before any timeout is raised.** Features: none.

Raising a timeout is the last resort, after the test does less work.

Check: untestable: process rule for agents about test timeouts

## d181

**Requests to outside sites use a neutral client name; the maintainer's e-mail address and the people of Keri never go into a file.** Features: none.

An automated request names a generic client (`reference-reader/1.0`), never the project's name. The maintainer's e-mail address is never written to a file, memory, commit or message; when the maintainer allows it for one purpose, it is passed for that run only. Photographs of Keri (the reference photographs and keri.ee's) are study only, never in git, on GitHub or published; people's faces are left out or blurred, and no file names a person.

Check: untestable: process rule for agents (outside requests, no personal data in files; the privacy check covers only part of it)

## d182

**After a green CI run and the merge word, a later commit that only touches docs or mail merges without a new run.** Features: none.

A pull request whose only change since its green check is a note in the docs is safe to merge; a broken main is fixed after. The merger checks that `git diff --stat <green sha>..HEAD` holds only docs or `projects/` files (a merge from main bringing in no code) and names the green commit in the merge message; any code change waits for CI.

Check: untestable: merge process rule for agents

## d183

**The painter works in big chunks, one scene or one overhaul per pull request, and shows the maintainer pictures to pick from.** Features: none.

One big pull request rather than many small ones: one scene or one major overhaul per pull request, never one table or stick at a time, planned as sketches, about 80% with previews, refining, final touches, with documents synced at the end or by the architect. The maintainer picks from pictures, so a pass offers real alternatives with a recommendation; pictures stay the maintainer's to merge (d166).

Check: untestable: painter work style, judged by the maintainer

## d184

**Threads keep taking the roadmap's items without asking between them, and items that do not overlap run in parallel threads.** Features: none.

On the roadmap flow, finishing one item is not a reason to stop and ask before the next; isolated items go to separate threads at once.

Check: untestable: process rule for threads

## d185

**A change the maintainer asks for in a thread is done in that thread's pull request; debt found on the way is fixed in scope or written as one tag.** Features: none.

Never answer the maintainer's ask with a follow-up issue. Code smells and duplicated values met on the way are fixed when small and in scope; otherwise related findings go into one `TODO` tag in the doc they belong to (with d116), and a limit's coupled constants are derived from one source.

Check: untestable: process rule for agents

## d186

**After a merge the maintainer is pointed to `main`, and a force-pushed or restarted branch is always said.** Features: none.

The maintainer tries changes by pulling `main`; a restarted branch makes `git pull` refuse with divergent branches. So a reply after a merge says to test from `main` (`git switch main`, `git pull`, `npm run dev`, Ctrl+F5) and, when a branch was rewritten, gives the commands to update the local copy.

Check: untestable: process rule for what agents say after a merge

## d187

**A side question in the chat is answered in the chat without a new thread.** Features: none.

A new thread only when the answer cannot be given without one.

Check: untestable: chat convention for threads

## d188

**A thread whose branch is held by a pull request waiting on someone else puts its next item on `<branch>-<topic>`.** Features: none.

Waiting work must not stall ready work, as when a save-format pull request holds a thread's only branch. The thread says so in its reply.

Check: untestable: process rule for threads

## d198

**No agent works on, pushes to or merges an item labelled `architect:blocker`, and only the maintainer removes that label; `needs:maintainer` is taken off by whoever added it.** Features: none.

The labels and their meaning are in `docs/architect/labels.md`: `architect:blocker` stops all agent work on the item, `needs:maintainer` marks a pull request waiting on the maintainer's look or answer, and `ci:e2e` and `ci:visual` only ask CI for extra jobs. Pass: no commit, push or merge by an agent on an item while it carries `architect:blocker`.

Check: untestable: label discipline on GitHub, checked by the reviewer and the maintainer

## d199

**The architect writes one playable goal at the top of `docs/architect/roadmap.md` each week, deletes once a month what nobody read or used, and keeps the roadmap ordered by gates with no dates.** Features: none. The weekly goal and the weekly run superseded by d283; the monthly deletion and the gates still hold.

The weekly run (retired by d283) wrote the goal in play terms with the two or three tags it needs, deletes one unused thing in the same docs-only pull request and asks the maintainer at most one question the axioms do not decide. Releases R1 to R5 and `Later pool` follow order and gates, a milestone and the roadmap change together, roadmap questions are the architect's, and when the week's goal and a maintainer's issue collide the goal wins (`docs/automation/work-model.md`, `docs/architect/roadmap.md`).

Check: untestable: the architect's routine and roadmap upkeep, judged by the maintainer

## d200

**A question the axioms do not settle is decided under AX-3 and marked, never waited on, except a step that cannot be undone.** Features: none.

The choice is written `AX-3 provisional: <question>; chose <option> because <axioms>` in the pull request body and as a one-line code comment where it sits, with a `TODO(architect)` tag in the feature file; a save-format bump, a deletion or anything outside the repository waits for the maintainer. Agents do not ask the maintainer a question the axioms answer; a question the architect passes on names the axioms checked and why none decided it (`docs/axioms.md` AX-3 and the escalation loop, `axiom-call` skill). Pass: `git grep "AX-3 provisional:"` finds every such choice and each has its `TODO(architect)` tag.

Check: untestable: a judgement rule for agents, checked by the reviewer on each pull request

## d201

**Only the maintainer approves a change to `docs/axioms.md`; each change comes as one pull request that names it and gets a ledger entry.** Features: none.

A lasting answer of the maintainer that generalises becomes a corollary proposed by the architect in a `TODO(architect)` tag in `docs/axioms.md`, never written in by an agent on its own (`docs/axioms.md`, escalation loop step 4; `log-decision` skill step 4).

Check: untestable: an approval rule for the maintainer, seen in the pull request

## d202

**Only a person runs `npm run docs:verify`; agents never stamp a doc as re-read.** Features: none.

`docs:verify -- <doc>` records the commit a person read the doc against, so `docs:stale` stays a true list (CLAUDE.md, Commands; d041); it refuses to run inside an agent session.

Check: `tools/docs/verifyGuard.test.ts` "refuses inside an agent session and runs for a person"

## d203

**`npm run test:coverage` fails below 90% of lines, branches, functions or statements in `src/core`, `src/io` and `tools/`.** Features: none.

The gate is set in `vite.config.ts` and runs in CI's `check` job; scene code in `src/game`, the command-line entry points, the two Vite plugins, the art rules' test and the painters' picture tests are left out (`docs/testing.md` section 5). It extends d042, which named only `src/core` and `tools`.

Check: `vite.config.ts` "thresholds: { lines: 90, branches: 90, functions: 90, statements: 90 }"

## d204

**Nothing is built that has no file in `docs/features/`, and no seam or abstraction is added that is not on the table of `docs/futureproofing.md` section 2 or in a feature file.** Features: none.

A later idea, such as the sprite extensions of `docs/sprites.md` section 7, gets its own feature file before any code; everything else is YAGNI (`docs/futureproofing.md` section 3). `npm run docs:check` fails on a feature id in code with no file.

Check: `tools/docs/lint.test.ts` "flags ids with no file in docs and in code"

## d205

**Work touching more than two files starts with a written plan of a few lines checked against the feature's file; one feature at a time, each commit about one change.** Features: none.

The plan is written before the change and compared with the feature's acceptance criteria in `docs/features/` (CLAUDE.md, Working agreements).

Check: untestable: a working habit of agents, judged by the reviewer

## d206

**A task is done only when the feature's acceptance criteria are met, `npm run check` passes, the docs it touched are updated and a short note says what was done and what was not verified.** Features: none.

The Stop hook (`.claude/hooks/stop-check.mjs`) runs typecheck, lint and the docs check on a changed tree and sends the agent back on a failure; a failure that is not the agent's own is said plainly. A feature is never marked done on a manual run alone when a unit or replay test can cover it (`docs/testing.md` section 6, CLAUDE.md Definition of done).

Check: `tools/docs/criteria.test.ts` "fails a done feature with a criterion that has neither a test nor [human]"

## d207

**Long test runs go out as one background task that is never polled, unit tests never run while end-to-end tests run, and Playwright never reuses a server it did not start.** Features: none.

End-to-end and full checks run in the background with their completion notice (no `sleep` loops or repeated status checks; the Monitor tool for a condition); long output goes to a log and only the summary and failing names are read; a failing end-to-end test is rerun alone before the code is suspected. Playwright on port 5180 (`PW_PORT` moves it) fails on a port already held, and `PW_REUSE_SERVER=1` is set only for a server the agent started on purpose (CLAUDE.md, Working notes; `docs/testing.md` section 7).

Check: untestable: how agents run long jobs on a machine, not a behaviour of the game

## d208

**For `src/core` and `tools` the failing test is written first, a bug a person found gets a test that reproduces it before the fix, and every GitHub issue that changes behaviour leaves a test, named for the behaviour and never for the issue number, that is never deleted, skipped or loosened without the maintainer's agreement.** Features: none.
