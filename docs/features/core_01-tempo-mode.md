# core_01: Tempo mode

The cursor follows the beat instead of waiting for the right key; timing windows tighten by level; gentle rhythm scoring and a grade for how long each note is held. Crits in battle (ft_Y_01) depend on it. Index: [FEATURES.md](FEATURES.md).

## Rules

1. `PlayMode` is the strategy interface (ft_0_08); `TempoMode` (`src/core/judge/tempo.ts`) is a second implementation beside Wait, so practice, battle and the preview call a mode (`docs/futureproofing.md` 1.2). `PlayMode.advance?(nowMs)` lets time pass; `PracticeController.advance(nowMs)` is called by the scene each frame (d038, d039).
2. Transport (`src/core/transport/transport.ts`, reads no clock): `start(atMs)`, a one-bar count-in, `tempoPercent` (core_03; above 100 is faster), `timeOfTick`, `tickAt` (negative in the count-in), `countIn`, `metronome()`. The first key press only starts the transport and is not judged.
3. Each step has a window of `windowMs` either side, cut to half the gap to its neighbours so windows never overlap. A right key in its window is judged with `timing` (error in ms, `on-time`/`early`/`late`, score 0 to 100); a wrong key in the window is a wrong note and time goes on; a key outside every window is ignored; a passed window gives `NoteMissed`. Pitch rules, chords, ties and the two-hand "together" count are those of Wait mode. The judge records `rhythmErrorMs` per step (d011).
4. Windows (`timing.ts`: perfect 60, on time 150, playing window 400 ms) are provisional and start much wider than MIDI-HERO's. They wait for latency calibration (slice d). Real latency on the target laptop in Chrome: median 77 to 129 ms, steady inside a run, not between runs, so calibrate per session, not once per device (`docs/hardware-notes.md`).
5. Results carry `timing` statistics (played, on time, early, late, missed, mean absolute error, score with missed as 0). The score is kept per note and feeds core_04 and core_07.
6. Score view is a per-player setting: Off, Colours, Scores (a picture of three played notes in the settings). Colours: black fading to grey is fine, yellow to orange is mistimed, red is missed or wrong; Scores adds the number 0 to 100 over the note (the numbers cover colour-blind players).
7. Wait or Tempo is chosen on the practice screen: a button at the left end of the tools strip (fermata for Wait, a note running forward for Tempo; tooltip "Wait: the music waits. Tempo: it runs."). A press saves the other mode for the player and restarts the piece in it, the click at that mode's default (on in Tempo, off in Wait); Free play stays on. The metronome button is core_02 (d043).
8. In Tempo mode the screen says "Press any key to start"; the first key starts the count-in (bubble counts 1 to 4, browser metronome clicks). There is no visible line: an invisible line at `playheadAt` turns every staff line, bar line and note it passes hard grey (`noteColor`, `StaffView.drawPlayhead`); a note already played or missed keeps its timing colour (a wrong note keeps red). The line runs the whole width of each bar at one speed, leads the bar by the right padding, waits at the last bar line until the page turns. Wait mode has no playhead. Places: `core/layout/playhead.ts`, `core/layout/scoreColour.ts`, `StaffView.setPlayhead/applyTimings`.
9. Hold grading (slice f, d093, numbers provisional in one config beside `TempoWindows`): expected release is the note's end on the transport's clock (a tie chain is one note). Full hold is at least `max(85% of the value, value - 80 ms)` (`holdOf`, `fullHoldMs`, `DEFAULT_HOLD_RULES` in `src/core/judge/timing.ts`), counted from the note's written start. Note score is press score times a hold factor falling linearly from 1 (full) to 0.5 (tap); a note is never missed for its length. Duration needs no latency calibration.
10. Hold edge cases: legato into the next note is right; holding past the end into a rest is not graded; a key pressed again with no note-off counts as released then; chords and two hands are graded per key; a lost note-off counts as full and a later note-off changes nothing; once CC64 is parsed a release under the pedal is not graded (`src/io/midi/parse.ts` drops control changes today; whether the EZ-220 sends the pedal is unverified, needs human). Inputs MIDI, on-screen keyboard, QWERTY (repeats ignored) and the virtual player (`holdMs`, `holdFraction`; default holds a key its written value less at most 30 ms or a tenth) all send note-off.
11. `AX-3 provisional:` in a looped section a note counts as held in full once held to the wrap: 50 ms before the next lap's first window opens, but never before the last window closes. An earlier release is graded against that moment.
12. A bar, phrase or piece completes only once every note starting in it has a hold result, so its event (battle attacks, result screen) comes up to one note value later. `ResultTracker` accepts steps finishing out of order. `JUDGE_EVENT_VERSION` is 2; version 1 events still type-check. `TimingStats.holds` counts `full` and `short`.
13. A note let go early turns yellow to orange by how early (the worse of press and hold shows) and its Scores number is the final score. Default is on (AX-1); Wait mode is unchanged.
14. Admin switch "Grade note length" (on by default, per device, admin hub behind the password): off, Tempo mode judges onsets only as before slice f. Kept in `pianor-admin/settings` (`src/core/admin/adminSettings.ts`, `schemaVersion` 1), read once at start (`GameContext.adminSettings`), not in any profile.
15. Save and stats: the save has a per-note timing list per attempt since v12 (d059), nothing fills it yet (slice e). `noteTimings` entries may carry `hold` (0 to 100 or null), absent in older saves (d069 rule 3). Each Tempo-mode practice-log bar keeps `short`; `notesCutShort` (`src/core/analysis/cutShort.ts`) sums it and Analyze writes "Bar N: K notes held too short" when K is above 0. Setting save version 4 came from 3 (slice c).
16. Tests: timing rules are tested in the core with injected time and replays (property tests: jitter inside windows keeps every note right, `advance` frequency changes nothing, every note ends played or missed); end-to-end only checks that the line runs and scores appear.
17. Not built: latency calibration tap-along screen (slice d, needs the real keyboard), a Start button, tempo percent on the screen (core_03), the sound of a missed note. Not verified: how it feels for the student, the 85% and 80 ms on the target laptop, the grey's contrast on the real screen.

18. **Start on the first note** (slice g): the mode button cycles Wait, Tempo, Tempo from the first note (`play.tempoStart`, no save bump); the press that completes the first step's keys starts the transport there (`Transport.startAtTick`), and the click joins on the next beat of the grid (`Transport.metronomeFrom`, the metronome's `firstBeat`).
19. **Auto reset** (slice g): `play.autoReset`, default off; `MissedBars` counts bars with notes and none played right, and at two (`AUTO_RESET_BARS`) the play starts over and waits for the start. AX-3 provisional: it waits instead of counting in at once; wrong keys alone do not save a bar; not while the game plays the piece or Kiur is at the door.
20. **The clock that follows the player** (slice h: in Tempo mode a few hiccups must not derail the rest of the piece; the strict clock stays for rigorous training). The strict clock runs on, so one late key falls outside its note's window, is taken for nothing, and every note after it is late too. The following clock (`TempoMode` with `follow`, `Transport.follow`, `FollowRules` in `src/core/judge/timing.ts`) works like a phase-locked loop:
    - **Phase.** Every step played puts the clock on its first press: the next note is due one written gap after the key the student really played, not after where the clock had got to. A slip is paid once, never carried on.
    - **Waiting.** When a step's window runs out the clock stands at the window's end until the step is played: nothing is missed, the playhead stands still, a wrong key is a wrong note of that step, and the right key counts as late by the window (its colour and score say so). A right key before the window, once the step before is done, is that note played early (score 0) instead of a key for nothing, and its length is counted from that press; a wrong key before the window is still no note, and so is the count-in before the first note. Known: a key that bounces on a repeated note is taken as the next note, played early.
    - **Period.** The gap from the step before, against its written length, is the pace just played; the clock's rate takes a quarter of the difference at each note (`gain` 0.25) and stays within 15% of the tempo that was set (`band` 0.15). A gap that was waited in sets nothing. With a band of 0 the tempo is kept and only the waiting is left (the "halting" clock, not on the screen).
    - Pitch rules, chords, the together count, holds and results are those of Tempo mode. `AX-3 provisional:` the gain, the band, and that a late note waits without limit.
21. **On the practice screen** (slice h) the mode button goes from the most forgiving to the strictest: Wait, the following clock (a running note under a fermata, "Tempo that follows you"), Tempo with a count-in, Tempo from the first note. The following clock is Tempo mode with `play.tempoClock: 'follow'` (optional, no save bump, absent reads as strict) and is started by the first note. It has no click (a click keeps one beat and this clock does not; the button says so). The auto reset (rule 19) never fires with it, since no note is missed, and a pass is saved at the tempo percent that was set, though the clock may have run up to 15% off it. When the player's own learning runs have measured a tempo for the piece (ft_1_32 rule 8), a new start is at that baseline instead of the last tempo played (`baselinePercent`).

## Acceptance criteria

- **core_01.AC1** The transport maps ticks to the clock at the tempo percent, with a one-bar count-in started by the first key press and a metronome in step (slice a).
- **core_01.AC2** `TempoMode` judges each press against the expected onset with timing windows that never overlap; a note whose window passes is missed; every note ends played or missed, never both (slice b).
- **core_01.AC3** The practice controller drives the mode in time (`advance`), and the screen shows a playhead and per-note score colours in the three score views, a per-player setting (slice c).
- **core_01.AC4** The latency between what the student hears and the keyboard's timestamps is calibrated per device (slice d, needs the real keyboard). [human]
- **core_01.AC5** The per-note timing is stored with each play for the stats (slice e).
- **core_01.AC6** A right note's score also counts how long the key was held: full when held at least the larger of 85% of its value (a tie chain as one value) and the value minus 80 ms; a tap scores half its press score; legato overlap and a lost note-off never lower it; a note is never missed for its length (slice f1).
- **core_01.AC7** Bar, phrase and piece results come only once every note that starts in them has a hold result (released, or its end has passed) (slice f1).
- **core_01.AC8** A note let go too early changes its colour, and its number in the Scores view, when it is released (slice f2).
- **core_01.AC9** A per-device admin switch "Grade note length" (on by default) turns slice f off; off, Tempo mode scores and times its results exactly as before slice f (slice f2).
- **core_01.AC10** Tempo mode can start on the first note instead of a count-in, a choice per player on the practice screen's mode button (Wait, Tempo, Tempo from the first note): nothing runs and no key is judged until every key of the first note or chord is down at once; that press puts the first note on the clock (a pickup keeps its beat), its keys count as on time, and the click joins on the next beat (slice g).
- **core_01.AC11** A per-player switch in Tempo mode: once two bars in a row that have notes pass with none played right (wrong keys do not count; bars of rests are skipped), the play starts over from its first bar as with the space bar, unscored, and waits for the start again (a key for the count-in, or the first note) (slice g).
- **core_01.AC12** With the following clock no note is ever missed: a step whose window has run out is waited for and its key is late by the window, a right key before the window is that note played early, every step played puts the clock on its press, and the tempo leans toward the pace played within the band; a waited gap does not move it (slice h).
- **core_01.AC13** The practice screen's mode button offers the following clock between Wait and Tempo, saved per player with no save bump; it starts on the first note, has no click, and starts from the tempo measured in the player's learning runs when there is one (slice h).
