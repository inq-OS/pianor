# Features

Quick reference for every feature: what it is, its scope, how much effort it is and where it stands. Each feature has its own file with the full scope, acceptance criteria and status; this page is the index. **The tables are generated** from the front matter of the feature files (`npm run docs:index`); to change a row, change the file. Feature ids follow `docs/decisions/workflow.md#d037`. <!-- docs:ignore -->

**Ids:**
- `ft_Y_XX` is a feature of iteration Y, number XX inside it. **Iteration 0 is the MVP**; 1 is the next one (the editor, Keri and its characters). `ft_Y_XX` with a letter `Y` is a feature whose iteration is **not decided yet**; when its scope is defined it gets its number (`ft_2_NN`, and so on). Ids change as we go; `d037` keeps the map.
- `core_XX` is **core behaviour**: how playing, practising and progressing work, in any iteration, that the rest of the game builds on. They are not tied to one iteration.
- Parts of a feature have a letter: `ft_1_02a`.
- A file is `<id>-short-name.md`.

**Effort** (to build, from today's code; done features have none):

| Rating | Meaning |
|---|---|
| trivial | can be done immediately; drops into the current architecture |
| simple | reasonable effort, no architectural limitation |
| medium | more effort, little architectural friction |
| large | more effort, medium architectural friction |
| high friction | needs expensive architectural changes or a pivot |

Legend: **Human** = needs the student, the keyboard or the maintainer's eyes; the agent prepares it. **Ask** / **confirm** (older files) = settled from the axioms (`docs/axioms.md`); a point they do not settle is an AX-3 provisional choice that stands until the maintainer or a playtest changes it.

## Completeness

Every feature file carries `completeness: N` (an integer, 0 to 100) in its front matter: how much of **its own scope** is built and checked by the means an agent has (code, tests, the virtual keyboard). Work only a person can do (`[human]` criteria, the student, the real keyboard) does not lower it; the **Human** column counts the tagged `[human]` criteria of a feature. How to rate (`docs/decisions/workflow.md#d048`):

- A feature with slices: the built slices weighted by effort (trivial 1, simple 2, medium 4, large 8) over all slices. Without slices: the share of its numbered scope items that are built (a half-built item counts a half). Nothing built is 0; a preliminary prototype gets what its built scope is worth.
- `effort: done` means 100, and 100 needs a done effort and, through `npm run docs:criteria`, a test for every criterion that is not `[human]` (`docs:check` fails otherwise). A split feature has no value: it is the effort-weighted mean of its parts.
- The summary is the mean of the features weighted by the effort they were planned with (a done feature has no rating left and weighs like a simple one, 2; high friction weighs 16); parts count, their split parent does not.

**MVP release criteria:** ft_0_00 to ft_0_17 done; the student can pick a level-appropriate piece, play it from staff notation on the EZ-220, see feedback, earn XP and level up, and a parent can add new approved pieces without touching engine code.

**Build order (slice first, so the student could try the core loop early):** ft_0_00, ft_0_01 (parallel with ft_0_02), ft_0_02, ft_0_05, ft_0_08, ft_0_06, ft_0_09a (thin practice slice, then **the first human playtest**), ft_0_07, ft_0_09b, ft_0_03, ft_0_04, ft_0_10, ft_0_15, ft_0_11, ft_0_12, ft_0_13, ft_0_16, ft_0_14; after the MVP, ft_1_02. Work in order unless a feature says it can run in parallel. Each feature ends with its acceptance criteria met, checks green (`npm run check`) and docs updated.

## Adding or changing a feature

- A new feature gets the next free number in its iteration (`core_XX` if it is core behaviour, `ft_Y_XX` while its iteration is open) and a file `<id>-short-name.md` that starts with front matter (`id`, `title`, `scope`, `effort`, `status`, `completeness` as rated above, none for a split feature; optional `depends_on`), then run `npm run docs:index`: the row appears in the right table above, by its id. Do not build a feature that has no file (see `CLAUDE.md`).
- A feature file starts with its title (`# <id>: Name`) and a line with its phase, status and a link back here, then: what and why, the numbered scope, **Accept:**, **Human:** (if any), and an estimate when planned. A done feature keeps a `Status:` paragraph saying what was done and what was not verified. Acceptance criteria may be tagged `- **ft_0_08.AC1** text` so that `npm run docs:check` can tie each one to a test that names it (or to `[human]`); a feature cannot be marked done without them; see `ft_0_08` and `docs/decisions/workflow.md#d041`.
- Decisions made while building a feature go to `docs/decisions/` and name the feature.
